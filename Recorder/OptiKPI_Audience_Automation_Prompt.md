# OptiKPI Audience Automation – End-to-End QA Prompt

Implement end-to-end automation for the OptiKPI Audience module.

Use the latest Audience JSON/recording provided as the source for the actual Audience flow, selectors, test data, and existing automation framework conventions. Do not invent selectors or UI behavior that is not supported by the provided recording/application.

## 1. Static Audience

1. Navigate to Audience.
2. Create a new Audience from scratch.
3. Configure criteria using the provided JSON/test data.
4. Preview and validate criteria/count.
5. Save as Static.
6. Validate successful creation and retained criteria.

## 2. Scheduled Audience

1. Create another Audience from scratch.
2. Configure criteria using the provided JSON/test data.
3. Preview and validate criteria/count.
4. Select Scheduled.
5. Select the required schedule/date from the test data.
6. Publish the Audience.
7. Validate the status transition from In Progress to Active.

### In-Progress Validation

Immediately after publishing:

1. Poll the Audience status instead of using a fixed sleep.
2. Detect the In Progress status while it is available.
3. While In Progress, open the three-dot actions menu.
4. Attempt applicable actions that should not be available during processing, such as View Report.
5. Validate the expected popup/message indicating that the Audience is still in progress.
6. Validate the restricted/disabled action behavior.
7. Continue polling until the status becomes Active.

### Active Validation

After the Audience becomes Active:

1. Open the three-dot actions menu.
2. Validate expected actions are available, including where applicable:
   - Edit Audience
   - View Report
   - Other Active-Audience actions
3. Confirm actions restricted during In Progress are now available.

Do not use a fixed sleep such as sleep(5). Use polling with a reasonable timeout.

Expected flow:

Publish Scheduled Audience
→ Poll status
→ Detect IN PROGRESS
→ Validate restricted actions + popup
→ Continue polling
→ Detect ACTIVE
→ Validate three-dot actions

## 3. Bulk Audience – Customer List Download

For the CSV upload scenario, use the existing Bulk Audience.

Identify the Bulk Audience based on the Audience where User IDs are not empty. Do not create an unrelated temporary Audience solely for this download when the existing Bulk Audience is available.

Flow:

1. Locate/select the existing Bulk Audience.
2. Open the Audience.
3. Trigger Download Customer List.
4. Validate that the download request starts.
5. Close the popup if applicable.
6. Continue working in the application while the download is processing.
7. Wait for the background download to complete.
8. Validate that the CSV is actually available to the automation runner.
9. Validate that the file is complete and usable.

### Download Validation

Do not consider the download successful only because the request was triggered.

Validate:

**Download started**
- Download action was triggered.
- Background processing begins.

**Download completed**
- CSV exists in the configured download directory.
- The file is no longer being downloaded.
- No temporary/partial download file remains.
- The CSV can be opened/read successfully.

## 4. CSV Upload / Retention Audience

Use the same CSV file generated by the Bulk Audience Customer List Download.

Do not use a separately committed/static CSV when the purpose is to validate the download-to-upload flow.

Flow:

Bulk Audience
→ Download Customer List
→ Background processing
→ CSV download completed
→ Capture downloaded CSV path
→ Create new Audience
→ Select CSV Upload
→ Upload the downloaded CSV
→ Create Retention/CSV Audience
→ Validate successful creation

Validate:
- The downloaded CSV is successfully passed into the upload flow.
- The CSV is accepted.
- The Audience is created successfully.
- The resulting Audience contains the expected uploaded customer data.

## 5. Audience → Campaign

1. Open a created Audience.
2. Select the option to create a new Campaign from the Audience.
3. Validate that Campaign creation opens successfully.
4. Validate that the correct Audience is selected/pre-populated.
5. Continue only if the expected Audience is correctly associated.

## 6. GitHub Actions / CI Compatibility

The automation must work locally and in GitHub Actions.

Do not depend on a local machine path such as:
C:\Users\<user>\Downloads\customer-list.csv

Instead:

1. Configure a known temporary download directory for the test runner.
2. Clean it before the download scenario.
3. Trigger Customer List download.
4. Poll until the CSV download is complete.
5. Capture the actual downloaded CSV path dynamically.
6. Pass that file path directly into the CSV Upload Audience flow.
7. Clean up temporary test files where appropriate.

The downloaded file must be generated and reused entirely inside the GitHub Actions runner.

## 8. General Automation Requirements

- Follow the existing project automation framework and coding conventions.
- Use stable selectors from the actual application/recording where available.
- Avoid brittle selectors and unnecessary fixed waits.
- Prefer explicit waits and polling for asynchronous operations.
- Make the download-to-upload flow dynamic and CI-compatible.
- Keep individual scenarios identifiable while allowing the Download → CSV Upload flow to run as an end-to-end dependency.
- Capture useful failure information for status, popup, download, upload, or Audience creation failures.
- Do not assume a short-lived status or popup will always remain visible; poll/capture it as soon as available.
- Do not mark an asynchronous operation successful merely because the initial request was accepted; validate the final state/result.
